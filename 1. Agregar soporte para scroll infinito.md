Analiza el proyecto existente, desarrollado con **Angular + .NET + MySQL**, e implementa las siguientes mejoras respetando la arquitectura, convenciones, patrones y estilo de código actuales del repositorio.

## 1. Agregar soporte para scroll infinito

Actualmente el inventario utiliza paginación tradicional basada en `offset`. Mantén esta funcionalidad sin romperla y agrega una segunda modalidad de navegación mediante **scroll infinito**.

### Backend (.NET)

- Reutiliza, cuando sea posible, el endpoint actual de inventario.
- Permite indicar el tipo de paginación mediante parámetros claros.
- Mantén soporte para paginación tradicional con `offset` y `limit/pageSize`.
- Agrega soporte adecuado para cargar registros progresivamente desde el frontend.
- Evita devolver todo el inventario en una sola petición.
- Mantén filtros, búsquedas y ordenamiento existentes funcionando en ambos modos de paginación.
- Devuelve la metadata necesaria para que el frontend pueda determinar si existen más registros, por ejemplo:
  - `items`
  - `total`
  - `hasMore`
  - `offset`
  - `pageSize`
- Optimiza las consultas de Entity Framework/MySQL para evitar consultas innecesarias y problemas de rendimiento.
- Si el proyecto ya tiene DTOs, services, repositories o algún patrón equivalente, reutilízalos en lugar de crear una arquitectura paralela.

### Frontend (Angular)

Agrega una opción para que el usuario pueda elegir entre:

1. **Paginación tradicional**
2. **Scroll infinito**

Para el modo de scroll infinito:

- Carga el primer bloque de registros normalmente.
- Cuando el usuario se acerque al final de la lista, solicita el siguiente bloque.
- Agrega los nuevos registros a los existentes sin reemplazar los anteriores.
- Evita realizar peticiones duplicadas mientras una carga está en progreso.
- Detén las peticiones cuando el backend indique que no existen más registros.
- Muestra un indicador de carga mientras se solicitan más elementos.
- Maneja correctamente errores de red.
- Si cambian los filtros, búsqueda u ordenamiento, reinicia el estado del scroll y vuelve a cargar desde el primer bloque.
- Limpia correctamente subscriptions, observers o listeners cuando el componente se destruya.
- Prioriza `IntersectionObserver` para detectar cuándo cargar más elementos, salvo que la arquitectura actual del proyecto tenga una solución equivalente ya implementada.

La paginación tradicional existente debe continuar funcionando igual que antes.

## 2. Crear un Data Seed para inventario

Implementa un mecanismo de **data seeding** que permita generar una cantidad configurable de registros de inventario para poder probar visualmente tanto la paginación tradicional como el scroll infinito.

El seed debe permitir generar **N registros**, por ejemplo:

```text
100
500
1,000
5,000
10,000
```

No debe ser necesario escribir manualmente cada registro.

### Características de los datos

Genera datos suficientemente variados y realistas para que el inventario sea fácil de inspeccionar visualmente.

Incluye variaciones como:

- Nombre de producto
- SKU único
- Categoría
- Precio
- Stock
- Descripción
- Estado
- Fecha de creación
- Fecha de actualización

Si el modelo existente contiene otros campos obligatorios, complétalos también.

Ejemplos de productos:

```text
Laptop Pro 14
Monitor UltraWide 34
Teclado Mecánico RGB
Mouse Inalámbrico Pro
SSD NVMe 1TB
Memoria RAM DDR5 32GB
Dock USB-C
Webcam 4K
Audífonos Bluetooth
Router WiFi 6
```

No repitas exactamente los mismos valores para todos los registros. Genera combinaciones y valores diferentes para que al desplazarse por cientos o miles de registros sea evidente que el scroll infinito está funcionando.

Los SKU deben ser únicos, por ejemplo:

```text
INV-000001
INV-000002
INV-000003
...
```

El stock y los precios deben variar dentro de rangos razonables.

## 3. Configuración del Seed

La cantidad de registros debe poder configurarse fácilmente, por ejemplo mediante:

- `appsettings.Development.json`
- variable de entorno
- argumento de ejecución
- constante claramente localizada

Prefiere el mecanismo que mejor se adapte a la arquitectura actual.

Ejemplo conceptual:

```json
{
  "DataSeed": {
    "Enabled": true,
    "InventoryCount": 5000
  }
}
```

El seed:

- Debe estar pensado principalmente para desarrollo/testing.
- Debe evitar insertar los mismos datos nuevamente cada vez que inicia la aplicación.
- Debe poder deshabilitarse fácilmente.
- No debe borrar datos existentes de forma accidental.

## 4. Base de datos y rendimiento

Como se utilizarán miles de registros:

- Revisa que las consultas utilizadas por inventario estén correctamente paginadas.
- Evita cargar la tabla completa en memoria antes de aplicar `Skip/Take`.
- Aplica filtros, ordenamiento y paginación directamente en la consulta SQL mediante Entity Framework.
- Revisa si los campos utilizados frecuentemente para búsqueda, filtrado u ordenamiento necesitan índices.
- No agregues índices innecesarios.
- Evita problemas N+1.

## 5. Experiencia de usuario

En la pantalla de inventario agrega un selector sencillo, por ejemplo:

```text
Modo de navegación:

( ) Paginación
( ) Scroll infinito
```

O utiliza un selector/toggle equivalente que encaje con el diseño existente.

Cuando se seleccione scroll infinito:

- Oculta los controles de paginación tradicionales.
- Mantén visible el listado actual.
- Muestra un loader al cargar más registros.
- Cuando no existan más elementos, muestra un mensaje discreto como:

```text
No hay más registros.
```

## 6. Criterios de aceptación

La implementación se considera terminada cuando:

- La paginación tradicional existente continúa funcionando.
- El usuario puede cambiar entre paginación tradicional y scroll infinito.
- El scroll infinito carga nuevos bloques sin duplicar registros.
- Los filtros y búsquedas funcionan correctamente con scroll infinito.
- Cambiar filtros reinicia correctamente la carga.
- El backend nunca devuelve innecesariamente todos los registros.
- El seed permite configurar la cantidad de registros.
- Es posible generar al menos 5,000 registros para probar el comportamiento.
- Los SKU generados son únicos.
- El seed no duplica registros en cada inicio de la aplicación.
- La solución compila correctamente tanto en Angular como en .NET.
